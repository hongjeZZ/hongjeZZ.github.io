# 블로그 발행 정책

> 위키→블로그 발행 시 **표절(타사 콘텐츠)**과 **기밀 유출(사내 정보)**을 막는 2단 게이트.
> **대원칙 — fail closed**: 출처가 불분명하면 발행하지 않는다. 의심되면 막는다.
> 계기: `jvm-warmup`(카카오페이·LINE·Baeldung 종합)을 1인칭 경험으로 초안화한 사건 = 표절+경험 날조.
>
> **표절의 대상 = 사람이 쓴 "글"이지, 기술의 "사실"이 아니다.** 남의 산문·서사·고유 분석·개인 예제를 베끼는 게 표절이다. 반면 API·스키마·설정·공식 YAML·기술의 객관적 구조 같은 **공개 사실**은 출처를 밝히고 **위키 내용 그대로 충실히 옮겨도 표절이 아니다**(정확하니 오히려 권장). cite-only가 이 사실 레이어까지 "내 예제로 바꿔라"로 축약하게 두지 않는다 — 그게 argo 글이 빈약해진 원인이었다.
>
> **⚠ 상태(v0.3)**: 게이트 로직(`provenance-gate.py`)은 fail-closed로 구현·검증됨. 배선 현황: **Gate2(기밀)는 pre-commit 훅이 `_posts/` 커밋 시 자동 차단**(`ALLOW_PUBLISH=1`만 명시적 우회). **Gate1b(표절 overlap)·Gate2는 blog-publish 백테스트 축에서 자동 호출.** post-reviewer 서브에이전트의 HARD block은 `_posts/` 이동 전 필수 — `/draft-post` 경로는 사람이 검토(또는 post-reviewer 실행)하고, 위키 `/ingest-to-blog`는 block 0건일 때 post-reviewer를 자동 실행해 PASS여야 PR·머지까지 진행한다. 자동 "통과"를 맹신하지 말 것. fail-closed.

## Gate 1 — 출처 적격성 (표절 방지) · 선택 단계

위키 페이지의 **`provenance:` 필드**(ingest 시 stamp — 권위 신호)로 분류한다. 필드가 없는 legacy 페이지는 `sources:`가 가리키는 raw frontmatter의 clip 마커(`clipped_at`/`domain`/`tags: clipped`)로 추론한다(fail-closed).

| `provenance:` | 감지 신호(ingest 자동 판정) | 발행 |
|---|---|---|
| 🟥 **third-party** | raw에 `clipped_at`/`domain`/`tags: clipped` + 도메인이 회사·개인 블로그(kakaopay·linecorp·tistory·velog·toss·woowahan·baeldung·medium…) | ❌ **cite-only** (원문 재사용 금지·인용/참고만) |
| 🟥 **internal** | `sources:`가 `sdd/` 또는 raw가 k8s YAML(`spec:`/`kind:`), 사내 제품·아키텍처(내부 코드명 등) | ❌ 기본 금지(Gate2 레닥션 통과 시 한정) |
| 🟦 **reference** | 도메인이 공식 docs(spring.io·kubernetes.io·aws·redis.io…) | ⚠️ **cite-only** (인용 OK, 소유 주장 금지) |
| 🟩 **own** | clip/사내 마커 없음(내 노트·실험·의견) | ✅ 가능 (+ Gate 2 **항상**) |
| ⬜ **mixed / unknown** | 출처 혼합·없음·MISSING | ⛔ **검토 보류(fail closed)** |

### 🟥 third-party 처리 규칙 (가장 중요)
- **핵심 = cite-only.** 금지되는 건 **Obsidian 웹클리핑한 raw 텍스트(원문) 자체를 가져다 쓰는 것**이다. 그 주제로 **내가 직접 이해·정리한 글**을 쓰고, 원글을 **참고자료에 넣어 인용(따옴표+출처)하는 것은 정상**이다.
- **원문을 1인칭 경험으로 재작성 금지.** ("제가 겪었습니다 / 저희는 ~로 시작했습니다" = 표절 + 경험 날조)
- 유일 허용 형태 = **명시적 "학습 정리/리뷰" 글**:
  1. 제목·도입에 정리 글임을 밝힌다 — *"카카오페이·LINE 사례로 공부한 JVM 웜업 정리"*.
  2. **모든 출처를 본문과 `참고 자료`에 명시**(원저자·회사·URL).
  3. **1인칭은 내가 실제로 한 것에만** — 직접 돌린 실험, 내 의견, 내 환경 적용. 안 한 걸 했다고 쓰지 않는다.
  4. 핵심 문장·구조·도표를 그대로 옮기지 않는다(요약·재구성, 직접 인용은 인용부호).
- 블로그 정체성이 "개발 학습 노트·TIL·기술 정리"라 이 형태는 **합법**이다. 단 **출처 명시 + 경험 날조 금지**가 절대 조건.
- 🟩 own 글의 1인칭은 quality-profile §3 기준(무용담·오판담·감정 토로 없이 최소한). 🟥면 **3인칭 인용**("카카오페이는 ~했습니다")으로 전환.

### cite-only 정량 한계 (기계 검증 — `provenance-gate.py --overlap`)
🟥 third-party·🟦 reference 주제로 쓸 때, 아래를 넘으면 **재작성이 아니라 표절**이다. 게이트와 (배선될) post-reviewer가 **같은 수치**로 검사한다.

**재사용 OK (충실히 재현해도 표절 아님)**
- **기술의 객관적 사실 — 양 제한 없음**: API·클래스·메서드·설정키·기본값·CLI 플래그·에러 코드·버전·복잡도·동작 순서. "공개 사실"이라 빠짐없이 담아도 된다(축약하지 말고 충실히).
- **공식 스키마/설정 YAML·코드 예제 — 그대로 재현 OK**: 공식 문서의 `kind:`/`spec:`/ConfigMap 같은 스키마·설정 예제는 *그 기술을 정확히 쓰는 정답 형태*라 사실에 해당한다. 출처를 밝히면 위키에 있는 그대로(또는 최소 각색해) 실어도 된다 — **억지로 "내 예제로 교체"하지 않는다.** (저자가 지어낸 *서사형* 예제·고유 시나리오를 베끼는 것과는 구분.)
- **내 위키 내용**: 내가 ingest로 직접 정리한 위키 본문(한국어 요약·구조·예제)은 내 글이므로 그대로 충실히 옮겨도 된다. (단 위키 본문이 *타사 글을 clip 마커 없이 손요약*한 것이면 own이 아니다 — `sources:`가 외부 URL을 가리키면 clip 마커가 없어도 그 페이지는 cite-only로 보고 수동 stamp. 손요약이 own으로 떨어지면 '충실 재현'이 표절 세탁이 될 수 있음.)
- 출처 저자의 **산문 인용**은 출처당 1개 ≤ 40단어 `>` 블록인용 + 바로 아래 출처 표기. (한 출처 인용 합계 ≤ 90단어)
- **내가 직접 실행한** 코드·로그·측정치.

**재사용 금지 = 저자의 "글" 레이어 (기술 사실은 위 '재사용 OK')**
- 금지: 출처 저자의 **산문 문장**(인용 한계 초과), 그 저자의 **서사·해석·고유 분석**, 저자가 지어낸 **개인 예제/시나리오/데이터셋**, 1인칭 경험, 출처 글 *한 편*의 **소제목 구성을 통째로 답습**.
- 허용: 기술의 객관적 사실·스키마·공식 YAML·기술 자체의 구조는 위 '재사용 OK'대로 충실히 재현(표절 아님).
- 정량(저자 산문에만 적용): **인용부호 밖 연속 25단어 초과 동일** 또는 **draft 8-gram의 15% 초과가 출처와 겹침** → 표절 차단. (게이트는 코드블록·YAML을 비교에서 이미 제외 — 사실 레이어라 표절로 안 셈.)

**구조 — 남의 "글 구성"만 안 베끼면 된다 (기술 구조는 예외)**
- 특정 출처 *블로그 글 한 편*의 소제목 순서를 통째로 답습하지 않는다(단일 글 목차 60%+ 복제 차단).
- 단, **기술 자체의 자연스러운 구조**(예: 컨트롤러→CRD→템플릿→실행기→아티팩트처럼 그 기술의 객관적 구성요소 순서)를 따르는 건 답습이 아니다 — 사실이다. 공식 문서 한 곳만 봐도 이 순서를 따라도 된다.
- 공식 스키마/설정 예제는 **교체 의무 없음**(위 '재사용 OK'). 저자가 지어낸 서사형 예제만 안 베끼면 된다.

**출처 표기 형식**
- **직접 인용(블록인용)**에는 출처가 붙어야 한다(표절 방어) — 단, 본문 괄호 `(출처: …)` 대신 **prose 도입 문장**(*"망나니개발자는 다음과 같이 설명한다:"*)이나 블록인용 바로 아래 출처 줄(*"— 저자, [제목](URL)"*)로 밝힌다.
- **그 외 본문에는 `(참고: …)`·`(출처: …)` 괄호 출처 표기를 넣지 않는다.** 비자명 차용은 prose로 출처를 언급하거나(*"~의 정리에 따르면"*) 기술명 인라인 링크로 처리하고, 전체 출처 목록은 마지막 **참고 자료** 섹션에서 한 번에 정리한다.
- **참고 자료** 섹션: 저자·제목·URL(접근일은 넣지 않음). 참고자료에만 있고 본문에서 한 번도 언급·인용되지 않은 URL → 차단(안 쓴 출처 = 가짜 인용/미표기 재사용).

**다이어그램·증거 이미지** (🟥/🟦)
- 모든 그림은 **내 모델/내 실행**으로 새로 그린다(출처 레이아웃 복제 금지). "증거 이미지"는 **내 실행 스크린샷**으로만 충족 — 없으면 증거 이미지 없는 B형 개념글로 둔다(가짜 증거 날조 금지).

**정리 글이 합법인 조건** (출처 종류로 갈림)
- 🟦 **reference(공식 문서) 사실 정리**: (a) 기술 사실·스키마·공식 YAML은 충실히 재현 OK · (b) 출처 저자 산문은 ≤40단어 인용 · (c) "이 글은 공식 문서를 정리한 노트입니다" + 출처 링크. **개인 실험·의견·경험은 있으면 좋지만 필수가 아니다** — 공개 사실을 정확히 정리하는 것 자체가 합법이다(억지 서사·억지 경험 불필요).
- 🟥 **third-party(블로그) 정리**: 위 (a)~(c)에 더해 (d) 내 고유 기여 ≥1(직접 실행·측정·의견)으로 단순 재탕이 아닐 것 · (e) 출처 저자 경험을 1인칭으로 쓰지 않음(3인칭 인용).

> **알려진 한계**: 출처를 **클립하지 않고 손으로 요약**해 raw에 clip 마커가 없으면 provenance만으론 못 잡는다. 이 경우는 `--overlap`(원문 대조)과 사람 검토가 유일한 방어선이다.

## Gate 2 — 민감정보 레닥션 (기밀 유출 방지) · 생성 단계 · 🟩 own 글도 항상

내 글이라도 발행 전 다음을 **스캔 → 치환 → 사용자 확인**한다. (own 글에도 사내 제품명이 섞일 수 있음)

| 유형 | 예 | 처리 |
|---|---|---|
| 회사·고용주명 | 실제 사명 | "한 회사 / 재직 중인 곳"으로 일반화 또는 제거 |
| 내부 제품·서비스·프로젝트 코드명 | deny-list(내부 코드명 등) | 익명화("사내 트랜스코딩 시스템") 또는 제거 |
| 티켓·이슈 ID | `FWM-\d+`, JIRA 키 | 제거 |
| 내부 도메인·URL·호스트·IP | `*.internal`, 사설 IP(10./172./192.168.) | 제거·마스킹 |
| 자격증명·시크릿 | 토큰·키·비밀번호·커넥션 문자열 | **절대 금지** · 제거 |
| 고객·PII | 고객사명·개인정보 | 제거 |
| 비공개 수치·아키텍처 | 내부 SLA·트래픽·토폴로지·내부 메트릭 | 일반화 또는 사용자 확인 |

- **결정론적 1차**: `provenance-gate.py`가 `blog-sensitive-terms.txt`의 단어/정규식을 본문에서 grep → 발견 시 차단·표시.
- **LLM 2차**: post-reviewer가 문맥상 민감 정보를 추가 판단(deny-list에 없어도).
- 발견 시 **사용자 확인 후에만** 진행. 적중 상태로 자동 발행하지 않는다(pre-commit이 커밋을 막는다).

## 외부 자산·이미지 (라이선스·날조 금지)

- 웹 이미지는 **라이선스 명확한 것만**: 공식 docs 다이어그램(출처 표기)·CC·Wikimedia·직접 생성. 불확실하면 **넣지 말고 mermaid로 대체**.
- 모든 외부 이미지는 `assets/img/<slug>/`에 **로컬 저장 + 출처·라이선스 캡션**(핫링크 금지).
- **cite-only 글(🟥)**: 출처의 원본 그림·표·스크린샷 복제 금지(quality-profile §5). mermaid·직접 작성만.
- **로컬 테스트 결과·콘솔·벤치마크 스크린샷은 사용자가 직접 캡처** — LLM 생성·날조 금지. 없으면 `<!-- CAPTURE-NEEDED -->` 마커 + 사용자 질문.
- 공식 라이브러리 구현 코드·공식 예제는 코드블록 인용 가능(출처 링크). 길면 핵심부만.

## 파이프라인 통합

1. **선택** — `/draft-post`가 `provenance-gate.py`로 후보 분류 → 🟩 own만 기본 제시, 🟥는 "정리글 전용/금지"로 라벨, ⬜는 보류.
2. **생성** — 초안을 quality-profile §3(평이·충실 정리체) 기준으로 작성(타사면 3인칭 인용). Gate2 deny-list grep 0건 확인.
3. **리뷰** — post-reviewer가 Gate1·Gate2를 **HARD block**: 미통과면 `_posts/` 쓰기·PR을 막는다(사람 확인 전까지).

> 도구: `provenance-gate.py <wiki-root>` 전체 분류 / `provenance-gate.py <page>` 단일 페이지 출처+기밀 스캔.
> deny-list는 `blog-sensitive-terms.txt`에서 **사용자가 직접 관리**한다.
